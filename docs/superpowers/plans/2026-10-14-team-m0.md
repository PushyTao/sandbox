# M0 团队实施与集成计划

> 执行方式：已配置的 Multica 团队成员在独立任务分支工作，研发负责人集成；以平台任务为状态来源，不用临时子代理代替持续交接。

**目标：** 恢复既有 M0 历史，完成可评审的跨平台可行性证据、接口草案和安全/测试出口，再启动已获产品决策支持的 M1。

**架构：** 本阶段保留技术方案 v0.2 的组件和信任边界。M0 的 Python 标准库探针只运行固定合成实验，不是生产执行服务。Rust core、平台适配与 stdio RPC 是待决路线及实验合同，不预先冻结。

**技术栈：** 现有探针为 Python >=3.8；Linux 实验依赖实际可用的 bubblewrap 与 namespace；原生 Windows 实验调用 Job API。生产技术栈由 D3 决策。

**依据：** 根目录 `2026-09-30-agent-sandbox-design.md` 和同内容存档 `docs/design/2026-09-30-agent-sandbox-design.md`；父任务 PUSH-2（`01a13ac9-ac49-7d80-b0ac-06ee13f13f37`）。

## 全局约束

- 关键语义未定前不冻结外部 API；D1–D7 保持待确认，文档 §14.1 明确允许先推进 M0。
- 所需能力缺失、策略不可表达、初始化或自检失败时不运行负载；没有无隔离兜底。
- 不可信负载不能自批权限；授权不能越过硬策略；限制在负载运行前生效。
- Windows、Linux、macOS 分开验收；WSL 不等于原生 Windows，跳过不等于通过。
- 不更改宿主账户、ACL、防火墙、内核设置和信任库，不发布产品、不增设团队或自动化。
- 保留有意义的提交，独立 review 后以 merge commit 集成到 main；不得把任务已分派称为项目完成。

## 需求、优先级与缺口

| 优先级 | 需求/风险 | 验收与出口 |
|---|---|---|
| P0 | 恢复未推送的历史 | PUSH-1 的 7 个原 SHA 均为集成分支祖先，用户 main 两个已有提交也完整保留 |
| P0 | 安全边界及失败关闭 | 固定版本、真实环境正反向证据；不可表达的 hardlink/未来保护名称策略拒绝或采用经验证方案 |
| P0 | 可信审批与工具路由 | 模型不可批准，file 与 exec 共用策略，控制与数据通道分离 |
| P0 | 三平台回收与安装风险 | 子孙进程、断连/崩溃、清理失败、权限和撤销按平台记录；没有环境则未验证 |
| P1 | 控制台范围遗漏 | 补“环境”定义、所有权、审批、日志和取消；原方案只有可信 UI 概念，不能用 CLI 替代控制台验收 |
| P1 | 接入兼容和可复现构建 | 官方版本与实际工具清单；wrapper/MCP 不等于现成工具的全部执行已接管 |
| P1 | runtime 复用比较 | 固定 release/commit、许可证及可运行比较；不能仅凭 README 决定自研或复用 |

## Stage 2：M1 启动门与首个可运行里程碑

D1–D7 未得到产品确认、M0 关键能力证据未齐备时，不启动生产安全边界或冻结公开 API。已向用户呈现推荐组合；未回复不能视为批准。系统版本/CPU 架构、控制台形态和会话所有权需在架构提案中明确。

第一个可运行里程碑必须贯通：

1. 在声明平台安装并运行 doctor，缺能力给出明确原因。
2. 通过管理控制台创建受限环境，展示工作区、有效策略与能力。
3. 沙箱外工具按实验后形成的版本合同提交 exec 和文件任务。
4. 控制台与客户端收到有界输出、结果和脱敏审计。
5. 可信宿主处理权限增量；模型与负载无法自批或持有 grant 秘密。
6. 取消/超时/断连按所有权规则终止执行，资源清理可验证，清理不完整不能报成功。
7. 按设计 §10.2 验收支持范围内全部必需项；未经验证的平台不进入支持列表。

M2 的 Windows 原生完整支持、域名代理、Node/Python 客户端、PTY/后台任务，以及 M3 Broker，按设计保留后续范围，不把当前研究 PR 当成这些能力的实现。若 D4 要求 Windows 首发或 D5 要求首版在线依赖安装，重排 M1 范围并保持安全门槛。
