## 结果与适用范围

| 检查 | 修复前 Python 3.8.5 | 修复后 Python 3.8.5 / 3.12.3 |
|---|---|---|
| 原三项 API 故障 | 三项通过，exit 0 | 各三项通过，exit 0 |
| Resume 前归组失败 | Resume 调用 0 次，错误为 AssignProcessToJobObject/5，却 assertion_passed=true、exit 0 | Resume 调用 0 次，目标调用、错误、阶段三项断言均 false；assertion_passed=false、exit 1 |

正常三项注入中 CreateProcessW/AssignProcessToJobObject/ResumeThread 的目标调用次数均为 1；后两项有正整数 PID、独立退出查询为 true。提前归组失败控制中真实 PID 也已退出，临时目录为空且根目录已删除。这里的通过是夹具按预期识别故障，不代表产品/真实宿主权限策略通过。元数据变异控制只验证 QA 判定拒绝不完整证据；缺失 PID 的变异结果不能当作该项独立 PID 清理证明。

## 修复内容与复现

旧断言仅检查 status、无 cleanup_errors，以及“没有 PID 或 PID 已退出”，所以在到达目标 API 前失败、丢失必要 PID 或阶段错配都可能被接受。新判定保存目标 mock；要求恰好调用一次、精确 operation/code=场景/5，并逐项核对 status、归组阶段、尚未运行、尚未到达正常关闭阶段、PID 是否应存在及独立退出证据。进程 PID 必须是非 bool 的正整数 DWORD；无效 PID 不调用观察 API。临时根目录删除结果也计入最终退出码。

`regress_windows_audit.py` 的 `early-assign` 与原评审复现一致：仅在 Resume 场景额外让 AssignProcessToJobObject 返回错误 5，Resume 的目标 mock 从未调用。工具先验证干净的固定 baseline，再加载其代码；每个控制在单独 Python 子进程中运行并保存报告及退出码。其余九个负向控制只改清理完成后的返回元数据，不修改 runtime 源码或真实资源清理。

在包含 `sandbox`、`qa-baseline` 的任务根目录执行：

```powershell
python -B sandbox/tools/qa/regress_windows_audit.py --source qa-baseline --output qa-recheck-py38
py -3.12 -B sandbox/tools/qa/regress_windows_audit.py --source qa-baseline --output qa-recheck-py312
python -B sandbox/tools/qa/regress_windows_audit.py --source qa-baseline --output qa-recheck-early.json --case early-assign
python -B sandbox/tools/qa/capture_m0.py --source qa-baseline --output qa-recheck-baseline
```

前两条预期 exit 0；第三条预期 exit 1；最后一条采集器 exit 0，但内部探针 exit 2。不存在的输出路径用于保留每次证据，禁止覆盖。
