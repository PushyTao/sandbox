## Git 保护与授权优先级

解决原设计 §4.3 与 §5.3/D10 的歧义：**能审批的只是显式登记的软限制；硬保护永远不受 grant 覆盖。** 原有 `protected_entries` 没有标明软类别时，按硬保护解释。不能因为用户点击“允许”或增加 writable roots 就把硬保护降成软保护。

策略解析结果将规则区分为 `hardDeny`、`softRestriction`、`baseAllow`，分类来自可信管理配置，不接受仓库配置或模型指定。普通 deny_read/deny_write/protected 默认进入 hardDeny。判定顺序：

1. 硬拒绝、上限或必需能力不满足：拒绝，不能申请覆盖它的授权。
2. 已登记软限制尚未被有效、精确的 grant 满足：拒绝或生成权限申请。
3. 有效允许集合包含该操作且所有其它限制仍成立：编译并启动。
4. 其余默认拒绝。

允许集合的普通合并仍取交集；grant 仅扩展其被命名的软规则，之后重新与硬上限相交。UI 展示完整权限差异与硬/软来源，不能只展示一条命令。

M0 基线维持 Git 元数据硬保护，**不提供 Git 写授权**。将来若需要 `git add/commit`，可信管理员必须先产生新的环境 revision、明确的软 Git 操作范围和新会话；该策略变更本身不通过 grant 完成。服务配置、审批凭据、helper、审计和 Agent 控制文件始终硬保护。Git broker 仅是候选，不能用“可信 broker”名义执行仓库可控 hooks 或任意 Git 参数。

不能笼统开放整个 `.git`：需识别 `.git` 指针、gitdir、commondir、子模块/嵌套仓库及共享 worktree 元数据，并限制 hooks/config/别名、外部 helper、环境覆盖和父目录替换。若不能在目标后端把允许的 index/objects/refs 更新与剩余硬保护分离，返回 `UnsupportedPolicy`。解析外部 gitdir 不产生新的读取权限。[Git 官方目录布局](https://git-scm.com/docs/gitrepository-layout)

“低权限 session 改写脚本，高权限 exec 再运行”的风险不因命令摘要或 session ID 消失。本提案默认串行写入信任域；增量授权前必须结束并确认回收旧权限负载，并采用可信快照/独立副本处理权限更高的任务。仅 argv 相同不是内容批准。若没有足够的隔离与共享资源证明，拒绝创建/执行该组合。
