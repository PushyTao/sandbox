# 管理控制台 M0 设计提案

日期：2026-10-22。任务：PUSH-8；状态：**待架构、安全和产品评审的静态设计**。本目录不包含产品 UI、可运行原型或服务实现，不冻结公开 API、框架、首发平台或 D1–D7。

控制台是“本机部署＋管理控制台＋沙箱外工具调用”定位的必要入口。原 [v0.2 技术方案](../../2026-09-30-agent-sandbox-design.md) §3.2 包含可信宿主集成层，但 §11.1 交付表和 §12 里程碑没有单列管理控制台。本提案补齐其职责、用户流程、接口需求和验收项，不能因表中缺项而把控制台排除在产品之外。

## 交付阶段补项

| 阶段 | 控制台应交付的内容 | 不能替代的证据 |
|---|---|---|
| M0（本任务） | 可评审需求、流程、权限边界、候选模型和接口需求 | 文档审核不证明隔离、鉴权、回收或跨平台可用 |
| 可选原型 | 在明确选定形态后验证交互、长任务与错误文案；模拟数据必须标识 | 原型或 mock 不能作为后端联调通过 |
| M1（建议增列） | 选定平台上，控制台通过真实本地服务完成环境配置、Agent 任务、可信审批、输出、取消及清理闭环 | 必须关联真实服务/后端日志和 OS 资源检查，覆盖验收矩阵；没有真实后端不得报通过 |
| M2 及以后 | 随平台与能力扩展增加后台任务、重连保活、PTY 等独立验收 | 不因通用 UI 能显示按钮而声称已支持 |

M1 的具体形态、首发平台和范围仍由 D1–D7 与架构评审决定。如果控制台不能随 M1 交付，需显式修改里程碑并记录产品取舍，不能用 CLI 或一张静态页面默认为已满足“管理控制台”。

## 评审边界

控制台负责呈现服务确认的状态、编辑有权管理的配置、发起操作和展示拒绝原因。本地服务最终校验身份、权限、策略、路径、资源范围与版本。隔离、资源限制、进程生命周期、文件权限和可信授权签发均由执行服务及其可信组件实现。

本目录中的字段和状态名用于讨论语义，均非已发布 schema。依赖基准是原方案 v0.2 §§3.2、6、11、12、14；目前没有可声明兼容的本地服务协议版本。架构师在 PUSH-3 协调 [C1–C6](lifecycle.md#待架构协调的候选决策)，安全、运行时、接入和发布角色分别提供其边界证据后，才能确定实现合同。
